# Project Board plugin

A dependency-free Phoenix plugin with thread tabs, a project page, and a managed background sidecar. It requires Node.js on the environment running Phoenix. Tasks persist by project; the sidecar records future conversation completions for its explicitly configured project.

Install this directory in **Settings → Plugins**, enable it, and grant the desired project access. Open **Project Board** from a conversation's Plugins panel, or **Project overview** from Settings. Select **Use for background work** to receive completion events. See the [user guide](../../../docs/user/plugins.md).

## Develop a plugin

The server CLI includes:

```sh
t3 plugin init /absolute/path/my-board my-board
t3 plugin validate /absolute/path/my-board
t3 plugin schema > phoenix-plugin.schema.json
t3 plugin install /absolute/path/my-board
t3 plugin request '{"action":"enable","pluginId":"my-board","enabled":true}'
t3 plugin reload my-board
```

In a source checkout, replace `t3` with `node apps/server/src/bin.ts` from the repository root. Commands that contact a running server accept `--base-dir /path/to/its/home`. `init`, `validate`, and `schema` work offline. Initialization refuses to overwrite an existing folder. Installation registers disabled code; it does not execute it.

Reload re-reads the manifest, stops existing processes, restarts an enabled sidecar, and invalidates open instances. Reopen the view to load its new HTML. Reload preserves data, configuration, and grants that are still requested by the new manifest. It never grants newly requested capabilities automatically.

The scaffold is a small self-contained board. This example additionally demonstrates a separate sidecar and project-scoped persistence.

## Package and process contract

Use `phoenix.plugin.json` with `apiVersion: 1`. The [manifest schema](../../../docs/phoenix-plugin.schema.json) is generated by `plugin schema`; [the contracts](../../../packages/contracts/src/plugins.ts) define the wire API. IDs use lowercase letters, numbers, dots, and hyphens, start with a letter or number, and are at most 64 characters. View IDs must be unique.

A package declares one stdio MCP server and its views. A view names an app-visible MCP tool whose `_meta.ui.resourceUri` identifies a `ui://` HTML resource. Manual opening supplies `{_phoenix: {projectId, threadId?}}` when a scope is available. Thread views are the default; `scope: "project"` allows opening without a conversation. Tools should also handle an empty argument object for older clients.

Each installation owns at most one MCP connection and one optional sidecar, shared across clients. MCP starts on demand. A sidecar starts on enablement and server startup, without needing a tab or agent. Configure one background scope per installation; partition your plugin's own data by project when serving several views.

Both processes run in the installed directory and receive:

- `PHOENIX_PLUGIN_ROOT`: the installed directory.
- `PHOENIX_PLUGIN_DATA`: persistent storage for this plugin ID.
- `PHOENIX_PLUGIN_CONFIG`: JSON configuration, merging manifest defaults with saved values.

Sidecars also receive `PHOENIX_PLUGIN_SCOPE` (JSON scope or `null`) and `PHOENIX_PLUGIN_BASE_DIR` (the owning server home). Processes receive an explicit environment rather than inheriting Phoenix credentials. Use absolute executable paths when necessary.

An optional `configuration` object declares fields by key, with `title` and a string, number, or boolean `default`. Settings renders these fields; saving restarts the plugin. This is ordinary configuration, not a secret store.

A sidecar declares `restart: "never"` or `"on-failure"`. Failure retries use exponential backoff with a five-retry crash-loop limit; a minute of stable execution resets that counter. A normal exit does not restart. Disable, uninstall, reload, and server shutdown stop owned processes, including pending retries. Logs retain the latest 32,768 characters in memory. Persistent data is never deleted by these operations.

## Context, bridge, and SDK

Bundle scripts and styles into the HTML resource. External resource loading and direct host access are blocked by the frame sandbox and content security policy. Use the MCP Apps JSON-RPC bridge, not browser fetches to server-local ports.

Phoenix supplies theme variables, locale, dimensions, platform, and `hostContext["phoenix/context"]`. The latter identifies the owning environment and bound project/thread, lists granted capabilities, and includes permitted workspace/thread metadata. Web views with file permission also receive bounded references to open workspace files. Context updates are subscriptions; reconnecting obtains a fresh snapshot. If the server no longer recognizes an instance, reopen it.

The source SDK is exported as `@t3tools/client-runtime/plugins/sdk`. Bundle it with your plugin:

```ts
import { createPhoenixPlugin } from "@t3tools/client-runtime/plugins/sdk";

const phoenix = createPhoenixPlugin({ name: "my-board", version: "0.1.0" });
phoenix.onContext((context) => console.log(context["phoenix/context"]));
phoenix.onResult(renderBoard);
await phoenix.initialize();
await phoenix.host({ type: "attach", text: "Investigate the selected task" });
```

`callTool` and `readResource` address only this plugin's MCP server. `host` sends a `phoenix/request` operation. Each request is checked against the instance's original scope, the installation's grants, and the client's permissions:

| Operation      | Required capability | Behavior                                                                                                                 |
| -------------- | ------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `context`      | `context`           | Current bound workspace and thread metadata                                                                              |
| `transcript`   | `transcript`        | Up to 20 message items, with the returned cursor for older pages; items larger than 32 KiB are marked truncated          |
| `files`        | `files`             | 32 KiB UTF-8 file pages using byte offsets; paths must resolve inside the bound workspace                                |
| `openFile`     | `files`             | Opens the workspace file; project-only pages show a paged text preview                                                   |
| `attach`       | `attach`            | Adds text to the bound conversation's composer without sending                                                           |
| `message`      | `message`           | Confirms, then queues a message on the bound conversation                                                                |
| `createThread` | `createThread`      | Confirms, then creates an empty conversation in the bound project, using an explicit, thread, or project model selection |
| `modelContext` | `modelContext`      | Replaces this view's temporary context, up to 16 KiB; empty text clears it                                               |

Transcript, attach, message, and model context require a bound conversation. Project pages offer a conversation selector. Instances never follow another device's active conversation. Changing permissions, disabling, restarting, or reloading invalidates existing instances. UI lifetime owns subscriptions; closing/hiding/disconnecting a view clears its transient model context. Server restart also clears it. A native caller opening an instance must release it explicitly with `plugin request` when finished.

The SDK bounds concurrent requests and applies a deadline. Call `dispose()` when your document's application unmounts. MCP resources/messages are capped at 2 MiB and requests have deadlines. No failed mutation is replayed automatically.

## Background events and native automation

A configured sidecar with `context` permission receives newline-delimited JSON on stdin:

```json
{
  "type": "thread.completed",
  "projectId": "project-id",
  "threadId": "thread-id",
  "runId": "run-id",
  "completedAt": "2026-11-25T12:00:00Z"
}
```

Only completions matching the configured and granted scope are delivered. Delivery is bounded and best-effort, not a durable event log. Deduplicate `runId` and write data atomically, as `sidecar.mjs` does. Clear the background selection with `{"action":"configure","pluginId":"my-board","scope":null}`. Sidecars may remain enabled for their own work without receiving Phoenix events.

Agents with full native access can discover `plugin_list`, register with `plugin_install`, and use `plugin_request` for lifecycle, grants, configuration, opening, and launching views. `launch` opens a tab for connected clients displaying its named conversation; it does not start an agent turn. Full-page project views can also be opened manually. Tool responses from `plugin_request` and `plugin_host` wrap their payload in `result`.

A trusted sidecar can use the same server CLI: `t3 plugin request '<JSON>' --base-dir "$PHOENIX_PLUGIN_BASE_DIR"` and `t3 plugin host '<JSON>' --base-dir "$PHOENIX_PLUGIN_BASE_DIR"`. Open with an explicit scope to obtain `instanceId`, call a granted host operation, then release it. Native operations have no client composer or file viewer: `attach` returns text for the caller to handle and `openFile` resolves a path. Native message/create operations are explicit automation, with no graphical confirmation. Reuse Phoenix's scheduler for timed work.

Native plugins execute as the server OS user. Capability grants protect the UI/API boundary; they do not sandbox native code or prevent it from reading other files accessible to that user. Never put authentication tokens or unrestricted RPC clients into plugin HTML.

## Provider decisions

Manual views, mobile views, and sidecars are provider-independent. Codex, Claude, Cursor, Grok, OpenCode, Antigravity, Kiro, Pi, Muse, and fx use their existing Phoenix MCP integration for plugin discovery and invocation; no custom plugin adapter is needed. The full tool profile advertises the plugin toolkit. A lean profile deliberately omits it; use manual plugin UI or the trusted CLI when appropriate. A provider unable to connect to Phoenix MCP can still describe tasks in text; it cannot claim to have opened a plugin. Replay remains the integration-test provider and does not exercise real model discovery.

There is no marketplace, automatic update distribution, native process sandbox, custom editor registration, or Antigravity manifest compatibility in this release.
